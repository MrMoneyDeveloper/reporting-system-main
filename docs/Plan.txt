## GAC Plan: Automated Ticket Summary + Productivity Reporting System

Your whiteboard is basically saying: **stop letting humans manually update things**, because apparently we enjoy building business processes on top of “please remember to send me this.” Tragic. 🧾

The correct build order is:

> **1. Google Sheet data engine first**
> **2. Automated Excel + email reporting second**
> **3. AI summary layer third**
> **4. Cloudflare site last**

The site is useless until the data pipeline is clean. Otherwise, you are just building a fancy window into garbage. Very modern, very corporate.

---

# 1. Final System Goal

You want one system that can:

| Area             | Purpose                                           |
| ---------------- | ------------------------------------------------- |
| Attendance       | Track who worked, when, and which shift           |
| Zendesk Tickets  | Pull actual ticket output by agent                |
| WFM Productivity | Pull logged productive/unproductive time          |
| Normalization    | Clean all raw data into one standard structure    |
| Reporting        | Generate daily, weekly, and monthly Excel reports |
| AI Summary       | Summarize performance for management              |
| Email            | Send summary + Excel automatically                |
| Site             | Allow users to view/download reports later        |

The system must support:

* **Daily reports**
* **Weekly reports**
* **Monthly reports**
* **Fiscal year logic**
* **Shift cutoffs**
* **Agent email mapping**
* **Enable/disable report schedules**
* **Manual reruns**
* **Audit logs**
* **Error logs**
* **Generated Excel files**
* **Email delivery**
* **Future web dashboard**

# 3. Key Principle

Do **not** hardcode people in Apps Script.

Bad:

```javascript
const agents = [
  "person1@email.com",
  "person2@email.com"
];
```

Better:

Use a sheet tab called:

```text
Agent Directory
```

That way, when someone leaves, you delete them from the sheet. No code change. No redeploy. No begging the script like it is a cursed toaster.

# 5. Data Pull Timing

You have three shifts:

| Shift | Time           |
| ----- | -------------- |
| Day   | 08:00 to 16:00 |
| Mid   | 16:00 to 00:00 |
| Night | 00:00 to 08:00 |

Pull data **5 to 10 minutes after shift close**.

| Pull                    | Time                                     |
| ----------------------- | ---------------------------------------- |
| Night shift pull        | 08:05                                    |
| Day shift pull          | 16:05                                    |
| Mid shift pull          | 00:05                                    |
| Daily report generation | 00:10 or 08:10 depending reporting logic |

### Important note

For daily reporting, decide what “one day” means.

You have two options:

## Option A: Calendar Day

```text
00:00 to 23:59
```

Simple, but mid shift ends at midnight and can become awkward.

## Option B: Operational Day

```text
08:00 to next day 08:00
```

This is better for your shift setup.

Recommended:

> Use **Operational Day: 08:00 to 08:00**

That means the full business day includes:

```text
Day shift:   08:00 to 16:00
Mid shift:   16:00 to 00:00
Night shift: 00:00 to 08:00
```

Then send the full daily report after the night shift closes:

```text
08:10
```

This is cleaner for operations and payment reporting.

# 6. API Pull Logic

## 6.1 Agent Filter Logic

The script starts by reading:

```text
Agent Directory
```

Then it filters:

```text
Active = TRUE
```

Then it builds an email list:

```text
[
  "agent1@email.com",
  "agent2@email.com",
  "agent3@email.com"
]
```

Then every API request only pulls data for those users.

---

## 6.2 Zendesk Ticket Pull

The Apps Script should:

1. Read active agents from `Agent Directory`
2. Get report window
3. Call Zendesk API
4. Pull tickets updated/solved in that window
5. Match tickets to assignee email
6. Write raw results to `Raw Zendesk Tickets`
7. Avoid duplicates using Ticket ID + Updated At or Ticket ID + Solved At

### Ticket fields needed

Minimum:

```text
Ticket ID
Assignee ID
Assignee Email
Status
Created At
Solved At
Updated At
Ticket Form
Group
Tags
Channel
```

---

## 6.3 WFM Pull

The Apps Script should:

1. Read active agents
2. Get report window
3. Call WFM API
4. Pull productivity/activity records
5. Match by agent email
6. Write raw data to `Raw WFM`
7. Avoid duplicate records using Agent Email + Date + Activity + Time Range

---

## 6.4 Attendance Pull

Attendance is not coming from API yet.

For now:

1. Maintain yearly attendance in Google Sheets
2. Include email or agent mapping
3. Script reads attendance records for the report window
4. Normalize into `Normalized Attendance`

Recommended approach:

Do **not** rely only on names.

Names are messy.

Use email as the matching key.

If you do not want visible emails in attendance, create a hidden mapping tab:

```text
Attendance Name Map
```

| Attendance Name | Email                                   |
| --------------- | --------------------------------------- |
| John S          | [john@email.com](mailto:john@email.com) |
| Jane Doe        | [jane@email.com](mailto:jane@email.com) |

Then the script can match:

```text
Attendance Name -> Email -> Agent Directory
```

# 7. Normalization Logic

Raw data must be cleaned into a standard format.

## 7.1 Normalize Attendance

For each attendance row:

```text
Date
Agent Email
Shift
Attendance Status
Expected Hours
Actual Hours
Late Minutes
```

Then calculate:

```text
Attendance Score
```

Example scoring:

| Status           |    Score |
| ---------------- | -------: |
| Present          |        1 |
| Late             |     0.75 |
| Sick with notice |     0.75 |
| Leave approved   | Excluded |
| Absent           |        0 |
| AWOL             |        0 |

---

## 7.2 Normalize Tickets

For each agent in the report period:

Calculate:

```text
Tickets Solved
Tickets Updated
Tickets Created
Forms Worked
Groups Worked
```

You can also create weighted ticket points later:

| Ticket Type           | Weight |
| --------------------- | -----: |
| Simple support ticket |      1 |
| Technical ticket      |      2 |
| Escalation            |      3 |
| QA / Review           |    1.5 |

But for phase 1, keep it simple:

```text
Tickets Solved = count of solved tickets
```

Do not overcomplicate it early. That is how projects go to die in a spreadsheet-shaped coffin. ⚰️

---

## 7.3 Normalize WFM

For each agent:

```text
Total Hours
Productive Hours
Unproductive Hours
General Task Hours
Productivity %
```

Formula:

```text
Productivity % = Productive Hours / Total Logged Hours
```

But exclude approved non-working time where needed.

# 11. AI Summary Logic

Do not send the AI raw rows if there are thousands.

That is expensive and dumb, which means someone will suggest it in a meeting. 🤖

Instead, send the AI the already-normalized summary.

## AI input should look like this:

```json
{
  "report_type": "daily",
  "period_start": "2026-06-04 08:00",
  "period_end": "2026-06-05 08:00",
  "shift_summary": [
    {
      "shift": "Day",
      "attendance_rate": 0.94,
      "productivity_rate": 0.81,
      "tickets_solved": 123
    }
  ],
  "agent_exceptions": [
    {
      "agent": "John Smith",
      "issue": "Low WFM productivity",
      "productivity": 0.42
    }
  ],
  "top_performers": [
    {
      "agent": "Jane Doe",
      "reason": "High ticket output and strong productivity"
    }
  ]
}
```

## AI output should produce:

```text
1. Top-level operational summary
2. Attendance concerns
3. Productivity concerns
4. Ticket output summary
5. Key risks
6. Recommended actions
```

Your thinking is mostly correct.

Because your operational day naturally ends after night shift:

```text
08:00 to next day 08:00
```

That gives you one complete business cycle:

```text
Day + Mid + Night
```

Clean reporting. Clean attendance. Clean payroll support. Less spreadsheet witchcraft. 🧙‍♂️
